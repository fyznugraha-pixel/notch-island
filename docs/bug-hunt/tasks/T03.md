### T03-01
- **ID**: `T03-01`
- **Judul**: Emergency kill-switch dipanggil sinkron di callback `WH_KEYBOARD_LL` dan menghilangkan notifikasi UI
- **Lokasi**: `src-tauri/src/taskbar_hotkey.rs:305-308` (memanggil `src-tauri/src/taskbar_safety.rs:130-156` dan `src-tauri/src/taskbar_manager.rs:348-402`)
- **Kategori**: Integrasi Windows
- **Keparahan**: `TINGGI`
- **Frekuensi**: `Kondisional`
- **Status Verifikasi**: `DUGAAN DARI KODE` `[BELUM DIVERIFIKASI DI DESKTOP ASLI]`
- **Langkah Reproduksi**:
  1. Aktifkan penggantian taskbar/flyout Gili dengan `hideWindowsTaskbar = true`.
  2. Ketika `explorer.exe` atau disk sedang lambat/sibuk (situasi umum yang memicu user memakai kill-switch), tekan `Ctrl + Alt + Shift + Backspace`.
  3. Amati eksekusi `low_level_keyboard_proc` dan state toggle di UI frontend.
- **Hasil Sebenarnya**:
  1. `low_level_keyboard_proc` memanggil `trigger_emergency_kill_switch(None)` secara sinkron di dalam callback `WH_KEYBOARD_LL` (berbeda dengan action lain seperti `OpenFlyout` atau `WinSoloStart` yang di-spawn ke thread terpisah).
  2. Di dalam hook thread, fungsi tersebut menjalankan disk I/O sinkron dengan `Mutex` (`log_taskbar_event` di `taskbar_logger.rs:17-49`, `std::fs::remove_file`), panggilan sinkron lintas proses ke `explorer.exe` (`SHAppBarMessage(ABM_SETSTATE)`, `ShowWindow`, `SetWindowPos`, `SetWindowRgn(..., true)` untuk primary dan seluruh secondary taskbar), serta `hide_taskbar_flyout()`.
  3. Bila durasi melebihi `LowLevelHooksTimeout` (~200-300 ms di Windows), input keyboard seluruh OS membeku dan Windows mencabut `WH_KEYBOARD_LL` secara diam-diam.
  4. Selain itu, argumen `None` pada `trigger_emergency_kill_switch(None)` menyebabkan `app.emit("taskbar-emergency-killed", ())` di `taskbar_safety.rs:153-155` tidak dijalankan, sehingga state UI pengaturan/navbar tidak mengetahui kill-switch telah aktif.
- **Hasil yang Diharapkan**:
  Callback `WH_KEYBOARD_LL` langsung mengembalikan `LRESULT(1)` dan men-spawn eksekusi `trigger_emergency_kill_switch` ke thread terpisah dengan menyertakan `AppHandle` (atau mendelegasikan via `AppHandle` tersimpan) sehingga tidak pernah melebihi `LowLevelHooksTimeout` dan UI frontend tetap ternotifikasi.
- **Bukti**:
  `src-tauri/src/taskbar_hotkey.rs:304-308`:
  ```rust
      match action {
          HotkeyAction::TriggerEmergencyKillSwitch => {
              trigger_emergency_kill_switch(None);
              return LRESULT(1); // Suppress event
          }
  ```
  `src-tauri/src/taskbar_safety.rs:130-156`:
  ```rust
  pub fn trigger_emergency_kill_switch(app_handle: Option<&AppHandle>) {
      log_taskbar_event(
          "system",
          "emergency_kill_switch",
          "ok",
          Some(serde_json::json!({ "reason": "user_hotkey_or_command" })),
      );
      restore_windows_taskbar_hard();
      ...
      crate::taskbar_flyout::hide_taskbar_flyout();
      if let Some(app) = app_handle {
          let _ = app.emit("taskbar-emergency-killed", ());
      }
  }
  ```
- **Dugaan Akar Masalah**:
  Desainer memindahkan aksi flyout/Start ke `std::thread::spawn`, namun lupa memindahkan `TriggerEmergencyKillSwitch` keluar dari callback `low_level_keyboard_proc` dan belum menyimpan `AppHandle` untuk pemanggilan dari layer hook.
- **Usulan Perbaikan**:
  Simpan `OnceLock<tauri::AppHandle>` saat `init_taskbar_hotkey_layer(app_handle)` (atau ambil dari state/manager) dan panggil `std::thread::spawn(|| trigger_emergency_kill_switch(APP_HANDLE.get()))` dari dalam `HotkeyAction::TriggerEmergencyKillSwitch` sebelum `return LRESULT(1)`.
- **Risiko Perbaikan**:
  Rendah; jika user menekan kill-switch berulang sangat cepat, perlu guard debounce/atomic agar tidak men-spawn banyak thread pemulihan sekaligus.

### T03-02
- **ID**: `T03-02`
- **Judul**: State `WIN_KEY_MASK` tertinggal saat Lock Screen/UAC dan modifier diabaikan untuk tombol Win
- **Lokasi**: `src-tauri/src/taskbar_hotkey.rs:170-178, 280-293` (serta `309-314`)
- **Kategori**: Integrasi Windows
- **Keparahan**: `TINGGI`
- **Frekuensi**: `Sering`
- **Status Verifikasi**: `DUGAAN DARI KODE` `[BELUM DIVERIFIKASI DI DESKTOP ASLI]`
- **Langkah Reproduksi**:
  1. Aktifkan `USE_GILI_START = true`.
  2. Kasus A (Lock Screen / UAC): Tekan `Win + L` untuk mengunci layar Windows (atau tekan `Win` lalu fokus berpindah ke jendela elevated / dialog UAC sebelum `Win` dilepas). Buka kunci layar dan langsung tekan tombol `LWin` sekali untuk membuka Start Menu.
  3. Kasus B (Modifier + Win): Tahan `Ctrl` (atau `Shift` atau `Alt`), tekan dan lepaskan `LWin`, lalu lepaskan `Ctrl`.
  4. Kasus C (Tap cepat < 2 ms): Tekan dan lepaskan `LWin` sangat cepat (< 2 ms).
- **Hasil Sebenarnya**:
  1. Pada Kasus A, `WM_KEYUP` untuk `LWin` dikirim ke secure desktop (`Winlogon`) atau jendela elevated (terblokir UIPI), sehingga hook non-elevated tidak pernah menerima `WM_KEYUP` `LWin`. State `WIN_KEY_MASK` tertinggal `BIT_LWIN` dan `WIN_KEY_INTERRUPTED = true`. Saat kembali ke desktop dan menekan `LWin`, `was_down` pada baris 171 bernilai `true` sehingga cabang `if !was_down` (baris 173-178) dilewati: `win_key_interrupted` tetap `true` dan `WinKeyDownInjectNeutralDelayed` tidak berjalan. Ketika `LWin` dilepas, `WinSoloStart` gagal dan Start Menu bawaan Windows yang muncul.
  2. Pada Kasus B, baris 280-282 memaksa `ModifierState::default()` setiap kali `is_win_key == true`, sehingga hook tidak mengetahui bahwa `Ctrl`/`Alt`/`Shift` sedang ditekan; menekan `Ctrl + Win` atau `Shift + Win` tetap memicu `WinSoloStart` dan menyuntikkan `0xE8`.
  3. Pada Kasus C, thread `WinKeyDownInjectNeutralDelayed` tidur 2 ms sebelum memanggil `inject_neutral_key()`, sehingga bila `LWin` dilepas sebelum 2 ms, tombol `0xE8` baru disuntikkan setelah `LWin` dilepas dan flyout mulai dibuka.
- **Hasil yang Diharapkan**:
  1. Saat `WM_KEYDOWN` untuk `LWin`/`RWin`, bit mask lain disinkronkan dengan `GetAsyncKeyState` fisik (atau saat terjadi `WM_KEYDOWN` untuk tombol Win yang bit-nya tertinggal padahal baru ditekan ulang setelah hilang fokus, `win_key_interrupted` di-reset dengan benar).
  2. Penekanan tombol `Win` ketika `Ctrl`, `Alt`, atau `Shift` sedang ditahan tidak memicu `WinSoloStart`.
- **Bukti**:
  `src-tauri/src/taskbar_hotkey.rs:170-178`:
  ```rust

            state.win_key_mask |= win_bit;

                state.win_key_interrupted = false;
                if flags.use_gili_start {
                    return HotkeyAction::WinKeyDownInjectNeutralDelayed;
                }
            }
        }
  ```
  `src-tauri/src/taskbar_hotkey.rs:280-293`:
  ```rust
    let mods = if is_win_key {
        ModifierState::default()
    } else {
        ModifierState {
            ctrl: is_vk_physically_down(VK_CONTROL.0),
            alt: is_vk_physically_down(VK_MENU.0),

            win_physically_down: if win_down_now {
                is_win_physically_down()
            } else {
                false
            },
        }

  ```
- **Dugaan Akar Masalah**:
  State `WIN_KEY_MASK` hanya di-reset pada tombol non-Win (baris 193-197), bukan pada tombol Win sendiri saat terjadi keydown baru setelah kehilangan `WM_KEYUP` di desktop aman/elevated; dan evaluasi modifier sengaja dinolkan untuk `is_win_key`.
- **Usulan Perbaikan**:
  Selalu baca `ctrl`/`alt`/`shift` dari `GetAsyncKeyState` bahkan saat `is_win_key == true`, tandai `win_key_interrupted = true` jika modifier lain aktif saat `Win` ditekan/dilepas, dan pada `is_win_key && is_down` verifikasi bit Win lain dengan `GetAsyncKeyState` serta tangani kondisi `LWin` ditekan ulang (non-autorepeat, yakni memeriksa `(state.win_key_mask & win_bit) == 0` atau timestamp/desktop change) agar state stale dari Lock Screen otomatis bersih. Untuk neutral key delayed, batalkan bila `WIN_KEY_MASK` sudah kembali 0 saat 2 ms berlalu.
- **Risiko Perbaikan**:
  Sedang; perlu menjaga kompatibilitas dengan unit test `evaluate_hotkey_event` yang menguji `LWin + RWin` bersamaan (`test_hotkey_lwin_and_rwin_held_simultaneously`).

### T03-04
- **ID**: `T03-04`
- **Judul**: `release_tray_overflow_lease` memakai `AtomicU32::try_update` sekali coba sehingga lease bocor saat contention
- **Lokasi**: `src-tauri/src/taskbar_manager.rs:39-52` (berdampak ke `src-tauri/src/taskbar_manager.rs:285-297, 510-515`)
- **Kategori**: Konkurensi/Race Condition
- **Keparahan**: `TINGGI`
- **Frekuensi**: `Kondisional`
- **Status Verifikasi**: `DUGAAN DARI KODE` `[BELUM DIVERIFIKASI DI DESKTOP ASLI]`
- **Langkah Reproduksi**:
  1. Sembunyikan Windows Taskbar (`TASKBAR_HIDDEN == true`).
  2. Picu dua operasi tray secara berdekatan/bersamaan (misalnya `open_windows_tray_overflow_from_flyout`, `invoke_system_tray_item`, atau `open_system_tray_item_menu`), sehingga satu thread memanggil `acquire_tray_overflow_lease()` (`fetch_add(1)`) tepat bersamaan dengan thread lain yang men-drop `TrayOverflowLeaseGuard` dan memanggil `release_tray_overflow_lease()`.
- **Hasil Sebenarnya**:
  `AtomicU32::try_update` di pustaka standar Rust hanya melakukan SATU kali percobaan `compare_exchange` tanpa loop retry. Jika terjadi contention pada `TRAY_OVERFLOW_LEASE_COUNT` antara dua operasi atomic tersebut, `try_update` mengembalikan `Err(current_value)` tanpa mengurangi nilai counter, lalu `.unwrap_or(0)` mengembalikan `0`! Akibatnya `TRAY_OVERFLOW_LEASE_COUNT` bocor (+1 selamanya), `has_tray_overflow_lease()` terus bernilai `true`, `restore_shell_tray_hidden_now()` selalu early return di baris 287, dan `Shell_TrayWnd` tidak pernah dikembalikan ke `cloak_and_hide_tray_hwnd` (`SW_HIDE`) oleh watchdog maupun caller.
- **Hasil yang Diharapkan**:
  Pengurangan lease count bersifat atomik dan selalu berhasil (memakai `fetch_update` atau loop CAS / `fetch_sub` dengan guard).
- **Bukti**:
  `src-tauri/src/taskbar_manager.rs:45-52`:
  ```rust
  pub fn release_tray_overflow_lease() {
      let prev = TRAY_OVERFLOW_LEASE_COUNT
          .try_update(Ordering::SeqCst, Ordering::SeqCst, |v| Some(v.saturating_sub(1)))
          .unwrap_or(0);
      if prev <= 1 && TASKBAR_HIDDEN.load(Ordering::SeqCst) {
          restore_shell_tray_hidden_now();
      }
  }
  ```
- **Dugaan Akar Masalah**:
  Penggunaan `AtomicU32::try_update` (single-shot CAS) dengan asumsi bekerja seperti `fetch_update` (CAS loop), lalu menelan kegagalan contention dengan `.unwrap_or(0)`.
- **Usulan Perbaikan**:
  Ganti `try_update` menjadi `fetch_update(Ordering::SeqCst, Ordering::SeqCst, |v| Some(v.saturating_sub(1)))` (atau gunakan `fetch_sub` jika selalu berpasangan dengan guard `TrayOverflowLeaseGuard`).
- **Risiko Perbaikan**:
  Sangat rendah; operasi atomic standar tanpa efek samping tambahan.

4. **`windows_pinned_apps.rs:881-893, 978-981, 1005-1007, 1026-1028` (`hicon_to_base64` & `extract_native_icon_from_path`)**: Bitmap `ICONINFO` (`hbmColor`, `hbmMask`), `HICON` hasil `PrivateExtractIconsW`/`ImageList_GetIcon`/`SHGetFileInfoW`, serta `HDC`/`HBITMAP` GDI pada jalur fallback dibebaskan dengan benar (`DeleteObject`, `DeleteDC`, `ReleaseDC`, `DestroyIcon`), dan `ICON_CACHE` dibatasi maksimal 512 entri (`BoundedPinnedIconCache`).

7. **`taskbar_safety.rs:184-248` (`switches_from_navbar_config_value`, `parse_navbar_config_from_settings_json`, `sync_switches_from_navbar_config_value`)**: Guard `entitled` dan flag `opt_navbar_default_off_v5` konsisten mencegah aktivasi fitur sebelum lisensi/migrasi valid.
