### T04-02
- **ID**: `T04-02`

- **Frekuensi**: `Sering`

### T04-04
- **ID**: `T04-04`
- **Judul**: Race condition `win.destroy()` asinkron pada `schedule_flyout_idle_destroy` vs re-open melalui `FLYOUT_BUILD_LOCK`
- **Lokasi**: `src-tauri/src/taskbar_flyout.rs:52-78` (dan `132-144`, `236-240`, `623-643`)
- **Kategori**: Konkurensi/Race Condition
- **Keparahan**: `TINGGI`
- **Frekuensi**: `Kondisional`
- **Status Verifikasi**: `DUGAAN DARI KODE` [BELUM DIVERIFIKASI DI DESKTOP ASLI]
- **Langkah Reproduksi**:
  1. Buka lalu tutup `taskbar_flyout` dan biarkan idle hingga genap `90` detik (`FLYOUT_IDLE_DESTROY_SECS`).
  2. Tepat ketika thread `schedule_flyout_idle_destroy` memanggil `win.destroy()` dan melepaskan `FLYOUT_BUILD_LOCK`, klik tombol dock untuk membuka flyout lagi.
- **Hasil Sebenarnya**:
  Di Tauri v2, `win.destroy()` bersifat asinkron (mengirim pesan penghancuran ke event loop utama) sehingga label `"taskbar_flyout"` belum terhapus dari map `webview_windows()` ketika `FLYOUT_BUILD_LOCK` dilepas. Thread `spawn_lazy_flyout_and_apply` memanggil `ensure_flyout_window_with_initial`, menerima `Some(win)` untuk jendela yang sedang dihancurkan (`141`), lalu menunggu `FLYOUT_READY` hingga 1500ms atau langsung dibatalkan saat `WindowEvent::Destroyed` (`236-240`) menyetel `FLYOUT_OPEN = false`. Pembukaan flyout gagal diam-diam.
- **Hasil yang Diharapkan**:
  Setelah memanggil `win.destroy()`, sistem menandai status "destroying" hingga `WindowEvent::Destroyed` selesai, atau melakukan tunggu/pembuatan ulang hanya setelah `Destroyed` terkonfirmasi.
- **Bukti**:
  `src-tauri/src/taskbar_flyout.rs:63-76` dan `136-143`:
  ```rust
  let _build_guard = FLYOUT_BUILD_LOCK
      .get_or_init(|| Mutex::new(()))
      .lock()
      .unwrap_or_else(|e| e.into_inner());
  if should_abort_idle_destroy(gen) {
      return;
  }
  if let Some(win) = app.get_webview_window("taskbar_flyout") {
      if !win.is_visible().unwrap_or(false) {
          FLYOUT_READY.store(false, Ordering::SeqCst);
          let _ = win.destroy();
          crate::memory_optimizer::schedule_working_set_trim(800);
      }
  }
  ```
  ```rust
  fn ensure_flyout_window_with_initial(...) -> Option<WebviewWindow> {
      let _build_guard = FLYOUT_BUILD_LOCK...;
      if let Some(win) = app.get_webview_window("taskbar_flyout") {
          return Some(win);
      }
  ```
- **Dugaan Akar Masalah**:
  `FLYOUT_BUILD_LOCK` dilepas segera setelah `win.destroy()` kembali, tanpa sinkronisasi terhadap selesainya `WindowEvent::Destroyed` di main thread.
- **Usulan Perbaikan**:
  Tambahkan flag/condvar `FLYOUT_DESTROYING` (atau `tokio::sync::Notify`) yang diset sebelum `win.destroy()` dan di-clear di `WindowEvent::Destroyed`, serta paksa `ensure_flyout_window_with_initial` menunggu penghancuran tuntas (atau buat label unik bila perlu) sebelum mengembalikan atau membangun window baru.
- **Risiko Perbaikan**:
  Sedang. Harus dihindari menunggu condvar di main thread agar tidak terjadi deadlock dengan event loop yang mengeksekusi `Destroyed`.

### T04-05
- **ID**: `T04-05`
- **Judul**: Race cold-start target switch, grace period `Focused(false)` 550ms, timpaan `LAST_FG_HWND` child HWND, dan fokus dicuri saat close
- **Lokasi**: `src-tauri/src/taskbar_flyout.rs:184-228` (dan `603-666`, `690-731`, `1055-1064`, `1134-1162`)
- **Kategori**: Konkurensi/Race Condition
- **Keparahan**: `TINGGI`
- **Frekuensi**: `Sering`
- **Status Verifikasi**: `DUGAAN DARI KODE` [BELUM DIVERIFIKASI DI DESKTOP ASLI]
- **Langkah Reproduksi**:
  1. Saat `taskbar_flyout` belum dibuat (cold-start), klik tombol `"start"` lalu cepat (< 300ms, selagi `FLYOUT_CREATING == true`) klik `"quickSettings"` atau tutup-lalu-buka target lain.
  2. Atau klik buka flyout lalu langsung (< 550ms) klik di luar flyout (area desktop / jendela lain).
  3. Atau fokuskan input pencarian WebView2 di dalam flyout lalu klik tombol flyout lain di dock, kemudian tutup flyout.
- **Hasil Sebenarnya**:
  1. Pada cold-start switch/re-open, panggilan kedua melihat `FLYOUT_CREATING == true` dan langsung `return` (`604-609`). Sementara `initialization_script` (`147-153`) menanam target awal (`"start"`) ke `window.__PENDING_TASKBAR_FLYOUT__`. Saat `TaskbarFlyoutApp.tsx:380-396` mount, ia menyetel `hasLiveStateUpdate = true` dari pending state usang tersebut lalu mengabaikan `get_taskbar_flyout_state()`, menyebabkan UI berkedip menampilkan target lama sebelum `eval` susulan berjalan.
