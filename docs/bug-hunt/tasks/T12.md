## 3. Rincian Temuan

### T12-01
- **ID**: `T12-01`
- **Judul**: Token sesi LAN prediktif (LCG berbasis waktu) dan oracle HTTP memungkinkan akses unduh/unggah tanpa otorisasi
- **Lokasi**: `src-tauri/src/shelf_server.rs:446-457`, `src-tauri/src/shelf_server.rs:557-568`, `src-tauri/src/shelf_server.rs:643-703`, `src-tauri/src/shelf_server.rs:848-856`
- **Kategori**: Keamanan
- **Keparahan**: `KRITIS`
- **Frekuensi**: `Selalu`
- **Status Verifikasi**: `TERBUKTI LEWAT UJI` `[BELUM DIVERIFIKASI DI DESKTOP ASLI]`
- **Langkah Reproduksi**:
  1. Pengguna mengaktifkan fitur Kirim ke HP atau Terima dari HP sehingga server HTTP bind di `0.0.0.0:8731`.
  2. Penyerang pada jaringan Wi-Fi yang sama melakukan polling `GET http://<ip-korban>:8731/d/x` tiap ~1 detik.
  3. Saat status HTTP berubah dari `404` ("Sesi transfer belum aktif") ke `403` ("Token download tidak valid"), penyerang mengetahui detik dimulainya sesi (jendela 1000 ms).
  4. Penyerang menghitung kandidat token menggunakan formula `(now ^ (now >> 7)) as u32` + LCG `1103515245 * x + 12345` untuk 1000 nilai milidetik tersebut dan mengujinya ke `/d/<kandidat>` atau `/u/<kandidat>/upload`.
- **Hasil Sebenarnya**: Token selalu ditemukan dalam <= 1000 percobaan tanpa rate limit, PIN, atau validasi tambahan, sehingga pihak lain di LAN dapat mengunduh semua file yang dibagikan atau mengunggah file sembarang ke `Downloads\Gili Shelf`.
- **Hasil yang Diharapkan**: Token sesi dibuat menggunakan CSPRNG (misal `getrandom` / `rand::rngs::OsRng`) minimal 128-bit entropi, disertai rate limiting dan tanpa oracle perbedaan status 404/403 antar sesi aktif vs tidak aktif.
- **Bukti**:
  Kode `src-tauri/src/shelf_server.rs:446-457`:
  ```rust
  fn generate_token() -> String {
      let charset = "abcdefghjkmnpqrstuvwxyz23456789";
      let now = now_millis();
      let mut rand_val = (now ^ (now >> 7)) as u32;
      let mut token = String::new();
      for _ in 0..7 {
          rand_val = rand_val.wrapping_mul(1103515245).wrapping_add(12345);
          let idx = (rand_val as usize) % charset.len();
          token.push(charset.chars().nth(idx).unwrap_or('x'));
      }
      token
  }
  ```
  Output uji `node tests/bug-hunt/T12_verify.mjs`:
  ```json
  "weakToken": {
    "realToken": "x4y99f7",
    "candidateCount": 1000
  }
  ```
- **Dugaan Akar Masalah**: `generate_token()` menggunakan LCG deterministik dengan satu-satunya sumber seed berupa `now_millis()` yang dipotong ke 32-bit, serta handler HTTP membocorkan status aktifnya sesi melalui perbedaan kode `404` vs `403` tanpa rate limit maupun pembatasan interface/PIN.
- **Usulan Perbaikan**: Ganti `generate_token()` dengan generator kriptografis (`rand::thread_rng()` / `OsRng`) dengan panjang minimal 16-24 karakter acak, kembalikan status `404` seragam saat token salah, dan tambahkan rate-limit / lockout sementara per IP setelah beberapa kegagalan 4xx.
- **Risiko Perbaikan**: URL QR sedikit lebih panjang, tetap aman terbaca dengan QR error correction `M` jika panjang token ~16 karakter.

### T12-03
- **ID**: `T12-03`
- **Judul**: File Shelf yang sudah dihapus bangkit kembali (resurrection) saat muat ulang dan seluruh data hilang jika JSON `localStorage` korup
- **Lokasi**: `src/services/shelfService.ts:259-349`
- **Kategori**: Data/Persistensi
- **Keparahan**: `TINGGI`
- **Frekuensi**: `Kondisional`
- **Status Verifikasi**: `TERBUKTI LEWAT UJI` `[BELUM DIVERIFIKASI DI DESKTOP ASLI]`
- **Langkah Reproduksi**:
  1. Pengguna menyimpan `fileA` (`addedAt: 1000`) dan `fileB` (`addedAt: 2000`) ke Shelf sehingga keduanya tersimpan di `localStorage` dan `shelf.json`.
  2. Pengguna menghapus `fileB` (atau `fileA`), memanggil `persistShelfFiles(next, false)`. `localStorage` langsung terbarui, sementara penulisan ke `shelf.json` masih tertunda debounce 300ms (atau gagal tulis).
  3. Aplikasi dimuat ulang / dibuka kembali lalu memanggil `loadPersistedShelfFiles()`.
- **Hasil Sebenarnya**: `loadPersistedShelfFiles()` membandingkan `Math.max(...addedAt)`. Saat `fileB` dihapus, `storeNewest (2000) > localNewest (1000)`; saat `fileA` dihapus, `storeNewest (2000) === localNewest (2000)`. Keduanya memenuhi `storeNewest >= localNewest` (`shelfService.ts:296`), sehingga data lama dari `shelf.json` dimuat dan file yang sudah dihapus muncul kembali. Selain itu, jika `localStorage` rusak JSON-nya, `JSON.parse` pada baris 277 melempar exception yang langsung membuang `storeData` yang sudah berhasil dibaca dan mengembalikan `[]`. `persistShelfFiles` juga memakai `Date.now()` beresolusi 1ms dan tidak menserialisasikan `flushToDisk()` sehingga penulisan lama yang lambat bisa menimpa penulisan baru.
- **Hasil yang Diharapkan**: Kesegaran data dibandingkan memakai nomor versi/timestamp revisi persistensi yang disimpan terpisah (bukan `addedAt` item), pembacaan `localStorage` dan `shelf.json` dibungkus `try/catch` terpisah, dan `flushToDisk()` diserialisasikan dengan antrean/mutex sekuensial.
- **Bukti**:
  Cuplikan `src/services/shelfService.ts:290-305`:
  ```ts
    const newest = (arr: StashedFile[] | null) =>
      arr && arr.length > 0 ? Math.max(...arr.map((f) => f.addedAt || 0)) : -1;
    const storeNewest = newest(storeData);
    const localNewest = newest(localData);

    let result: StashedFile[] = [];
    if (storeNewest >= 0 && storeNewest >= localNewest) {
      result = storeData!;
    } else if (localNewest >= 0) {
      result = localData!;
  ```
  Output uji `node tests/bug-hunt/T12_verify.mjs`:
  ```json
  "shelfResurrection": {
    "case1Count": 2,
    "case2Count": 2
  }
  ```
- **Dugaan Akar Masalah**: `loadPersistedShelfFiles()` memakai `Math.max(...addedAt)` sebagai proxy waktu modifikasi daftar, padahal operasi hapus item menurunkan atau tidak mengubah nilai `addedAt` maksimum.
- **Usulan Perbaikan**: Simpan metadata `updatedAt` / `revision` (counter monotonik) bersama array `files` di kedua penyimpanan (`localStorage` dan `shelf.json`), isolasi `try/catch` tiap sumber baca, gunakan counter monotonik untuk `lastPersistSeq`, dan rantai `flushToDisk()` secara sekuensial lewat promise queue.
- **Risiko Perbaikan**: Perlu mendukung format lama (array langsung tanpa wrapper `revision`) saat migrasi pertama agar data pengguna yang sudah ada tidak hilang.

- **Usulan Perbaikan**: Gunakan `useRef<Set<string>>` untuk `inFlightRef` dan state `failedThumbIds` (serta keluarkan `loadedThumbnails` dari dependensi efek), bersihkan key yang tidak ada lagi di `items`, dan tampilkan indikator gambar tidak tersedia bila gagal.
